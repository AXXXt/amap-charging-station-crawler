## 0. 先看这段：2026-09-16 14:38 起权威源换了

本次改动来自提交 `10e5eab`（"将 HENAN 任务调度切换为 MySQL 权威源"）。**改动前的文档、口头经验、旧脚本注释里的"SQLite 是权威源"已全部作废。**

| | 变更前（旧） | 变更后（现在） |
|---|---|---|
| **HENAN 任务**权威源 | ECS 上的 SQLite | **远程 MySQL** `henan_heavy_truck_charging_station_task` |
| MySQL 任务表角色 | 展示镜像（改了会被覆盖） | **权威源**（改了立即生效） |
| SQLite 角色 | 权威源 | HENAN 任务的**「启动导入缓存」**，运行期不再被更新 |
| 同步方向 | 运行期单条 SQLite → MySQL | 仅**启动时**一次 SQLite → MySQL 全量 UPSERT |
| 手机端 claim/ack/progress/complete/fail | 读写 SQLite | 直连 MySQL 事务 + 行锁 + 租约校验 |

**非 HENAN 的数据没有变**：`SITE_STATION_DETAIL` / `REGION_SCAN` 任务、设备表 `collector_device`、`station_observation` 仍然以 ECS 上的 SQLite 为准。

### 0.1 两条最容易踩的坑

1. **查 SQLite 看进度 = 看服务启动那一刻的旧快照**。HENAN 任务的真实进度只在 MySQL 里。
2. **任何重启都会用 SQLite 快照回写 MySQL**（`startup()` 里的全量 UPSERT 会覆盖 `status`/`attempt` 等）。所以：

> ⚠️ **只改 MySQL 虽然立即生效，但下次重启会被 SQLite 旧快照刷掉。**
> 要"既立即生效、又不怕重启"，必须 **MySQL 和 SQLite 两处都改**（§4.2 的脚本已经帮你两个都改）。

### 4.2 重跑数据：把「已完成」改回「待领取」★最常用

**首选：用云端脚本**（它替你做了备份 + **两个库一起改**，这是新架构下唯一"既生效又抗重启"的做法）：

```bash
ssh root@116.62.103.230 'cd /opt/amap-crawler && python3 reset_tasks.py'            # ① dry-run：先看要改几行
ssh root@116.62.103.230 'cd /opt/amap-crawler && python3 reset_tasks.py --apply'    # ② 执行（自动备份 SQLite）

# 变体：
#   连失败补采的任务一起归零：        --apply --include-failed
#   连站点详情任务一起重跑：          --apply --types HENAN_POI_DETAIL,SITE_STATION_DETAIL
#   只推 MySQL（临时，重启会回滚）：   --apply --mirror-only      ← 新架构下语义已变，见下方说明
#   只改 SQLite（不生效，等重启）：    --apply --skip-mirror      ← 仅用于"预置下次启动的状态"
```

**脚本在新架构下的真实行为**（务必理解）：

| 步骤 | 动作 | 效果 |
|---|---|---|
| ① | 备份 SQLite 为 `data/mobile_control.db.bak-<时间戳>` | 可回滚 |
| ② | `UPDATE scan_task ... WHERE type/status` 重置 SQLite | **本身不生效**（HENAN 已不从 SQLite 读），但让缓存与权威源保持一致 → **防重启回滚** |
| ③ | 按 `local_task_id` 把状态 `UPDATE` 到 MySQL 权威表 | **这一步才真正生效**（手机端下一次 claim 即可领到） |

所以两个变体要按新语义理解：

- `--mirror-only`：**只做第 ③ 步**，跳过 SQLite。MySQL 立即重置成功，但 SQLite 仍是旧状态 → **下次重启会被刷回去**。仅作临时手段。
- `--skip-mirror`：**只做第 ② 步**。当前**完全不生效**，要等服务重启才通过启动导入生效。仅在"想在维护窗口前预置状态"时使用。

**手工等价 SQL（理解用）**：新架构下标准做法是**两个库都改**。

```sql

   SET status='PENDING', attempt=0, recovery_attempt=0,
       lease_device_id=NULL, lease_token=NULL, lease_expires_at=NULL,

       progress=NULL, result_summary=NULL,
       available_at=NOW(), updated_at=NOW()

SELECT ROW_COUNT();     -- 看更新行数
```

```sql

BEGIN IMMEDIATE;
UPDATE scan_task
   SET status='PENDING', attempt=0, recovery_attempt=0,
```

> 只做第 1 步也能跑起来，但请记住"**下次重启会回滚**"这个代价——这也是为什么推荐直接用 `reset_tasks.py --apply`。

### 4.3 一致性校验（改完必做）

HENAN 任务现在只有一个权威源，所以校验的含义变了：**确认 SQLite 缓存与 MySQL 权威源一致**（不一致不会导致功能错误，但意味着"重启会回滚"这个雷还埋着）。

在 ECS 上执行（输出不一致行数，期望为 0）：

```bash
ssh root@116.62.103.230 'python3 -' <<'PY'
import re, sqlite3, pymysql
url = re.search(r'^EVCS_DATABASE_URL=(\S+)', open("/opt/amap-crawler/.env").read(), re.M).group(1).strip().strip('"')
m = re.match(r'mysql://([^:]+):([^@]+)@([^:/]+):(\d+)/(\S+)', url)
conn = pymysql.connect(host=m.group(3), port=int(m.group(4)), user=m.group(1), password=m.group(2),
                       database=m.group(5), charset="utf8mb4")
cur = conn.cursor()
cur.execute("SELECT local_task_id, status FROM henan_heavy_truck_charging_station_task")
authoritative = dict(cur.fetchall())
conn.close()
db = sqlite3.connect("/opt/amap-crawler/data/mobile_control.db")
cache = {r[0]: r[1] for r in db.execute("SELECT id, status FROM scan_task WHERE type='HENAN_POI_DETAIL'")}
db.close()
drift = [k for k in cache if authoritative.get(k) != cache[k]]
print("MySQL 权威源有", len(authoritative), "条 / SQLite 缓存有", len(cache), "条")
print("不一致行数 =", len(drift), drift[:5] if drift else "✅ 一致（重启不会回滚变化）")
```

## 5. 纪律：四条铁律 + 四条禁止

**铁律**

1. **HENAN 任务权威源 = MySQL**：看进度看它，改状态改它；SQLite 只是启动导入缓存。
2. **改状态必须两个库一起改**（或直接用 `reset_tasks.py --apply`）：只改 MySQL 会被重启回滚，只改 SQLite 当前不生效。
3. **`HENAN_MYSQL_AUTHORITATIVE=1` 之后没有"镜像兜底"了**：MySQL 被长事务锁住（`1205`）时，手机端的 claim/ack/progress/complete/fail 会**直接 500、采集中断**。旧的 `_sync_henan_task()` 已改成空实现（`return None`），不要再指望它。
4. **改前看 `LEASED`/`RUNNING`、改前备份、改后校验一致性**。

**禁止**

1. 🚫 不要在图形客户端里改了表却不提交（**现在会直接掐断手机端采集**）；
2. 🚫 不要在手机正在大批量领取任务时做全表重置（先确认 `LEASED`/`RUNNING`，必要时 `systemctl stop amap-api`）；
3. 🚫 不要把 `EVCS_DATABASE_URL` 里的口令贴到群里/截图里；
4. 🚫 不要手改 `site_exploration_charging_station_result` 之外的结果表然后指望"自动同步"—— 该表是 upsert 写入，重跑即覆盖，手工改动要自己想清影响面。

**留痕**：任何改状态的操作，请在 `cloud_service_ops.md` §10.5 的「实操留痕」表里补一行（时间 / 操作 / 备份文件名 / 执行人）。

## 6. 排障

| 现象 | 原因 | 处理 |
|---|---|---|
| 本机连不上 `121.41.56.201:3306` | 网络/白名单/防火墙 | 找管理员加你本机出口 IP；确认账号 host 允许（`'user'@'%'`） |
| MySQL 报 `1205 Lock wait timeout` | 有未提交事务锁着表 | ★**现在会导致手机端 500**。用带 `PROCESS` 权限的账号查并杀：<br>`SELECT trx_mysql_thread_id, TIMESTAMPDIFF(SECOND,trx_started,NOW()) FROM information_schema.INNODB_TRX;`<br>`KILL <thread_mysql_thread_id>;` |
| 手机端 claim/ack 返回 **500** | ① MySQL 锁表（1205）② 代码异常 | 先看日志：<br>`ssh root@116.62.103.230 "journalctl -u amap-api -n 100 --no-pager \| grep -A 5 'Traceback'"`<br>若是 `1205` → 按上一行杀事务，**本次架构后没有兜底，必须解锁才恢复**；<br>若是 `TypeError: the JSON object must be str...` → 见下方"已修历史问题" |
| **SQLite 与 MySQL 状态不一致** | SQLite 不再随运行期更新，属**预期现象**；但意味着"重启会回滚" | 若要消除，用 `reset_tasks.py --apply` 让两边一致；或接受差异（以 MySQL 为准） |
| 重启后任务进度"倒退" | 启动导入用 SQLite 快照覆盖了 MySQL | 属当前设计行为。**正在大批量采集时不要重启**；确需重启请先 `--apply --mirror-only` 之外的方式对齐——正确做法是让 SQLite 与 MySQL 先一致 |
| 手机端提示无任务 | 权威源（MySQL）里可领任务为 0 | 按 §4.1 查 MySQL；需要补充待领取任务按 §4.2 重置 |
| 服务异常 | —— | `systemctl status amap-api` / `journalctl -u amap-api -n 50 --no-pager` / 重启 `systemctl restart amap-api`（**注意启动约 50 秒**） |
| 权限不足无法看到锁 | `evcs_u` 无 `PROCESS` | 申请带 `PROCESS` 的账号，或请管理员代查 |

### 6.1 已修历史问题（2026-09-16）

**手机端 claim 全片 500：`TypeError: the JSON object must be str, bytes or bytearray, not dict`**

- 现象：`POST /api/v1/device-tasks/claim` 返回 500，日志堆栈指向 `_mobile_task_payload()`。
- 根因：新架构下 `_henan_mysql_row_to_task()` 用 DictCursor 读 MySQL，JSON 列已被解码成 `dict`；而 `_mobile_task_payload()` 仍按 SQLite 的约定无条件 `json.loads()`。
  因为 `_mobile_task_payload()` 是所有手机端接口的**唯一出口**（18 处调用），所以 claim/ack/progress/complete/fail 会一起崩。
  触发条件很隐蔽：**任务 `progress`/`result_summary` 为空时正常，一旦手机上报过进度就必崩**。
- 修复：新增 `_payload_object()` 兼容"JSON 字符串 / 已解码 dict / None"，替换了三处无条件 `json.loads()`。

## 7. FAQ

**Q：我只在自己电脑上操作，行不行？**
A：查数据 —— 行（本机直连 MySQL）。改**任务状态** —— 也能做（连 MySQL 即可，这是新架构带来的便利），但**别忘同步 SQLite**，否则下次重启回滚（§0.1）。

**Q：我直接改 MySQL 那张任务表，看着也变了啊？**
A：变了**而且立即生效**（这正是新架构的设计）。但**重启会被 SQLite 快照刷掉** —— 要么同时改 SQLite，要么直接用 `reset_tasks.py --apply`。

**Q：我按老文档改 SQLite 为什么没反应？**
A：因为 HENAN 任务已不从 SQLite 读取。改 SQLite 只在服务重启（启动导入）时才生效。要么改 MySQL，要么两个都改。

**Q：重跑会不会产生重复的采集结果？**
A：不会。结果表 `site_exploration_charging_station_result` 是 `ON DUPLICATE KEY UPDATE`（upsert），按站点覆盖更新。

**Q：能不能只重跑某几个站点？**
A：可以，但脚本目前是按"类型 + 状态"批量重置。要精确到站点：先在 MySQL 按 `local_task_id IN (...)` 改（记得清 `lease_device_id/lease_token/lease_expires_at/attempt`），再在 SQLite 用同样的 `id IN (...)` 改一遍保持一致。**改完务必做 §4.3 校验**。

**Q：改完要不要重启服务？**
A：改 MySQL 不需要（手机端下次 claim 立即读到）；改 SQLite 需要重启才生效；只有改代码才必须重启。
